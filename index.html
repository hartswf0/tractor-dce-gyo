TAXONOMY / MINIFIG OLOG
OBJECTS
Taxonomizer. An object is a taxonomy node (kingdom / phylum / class / order / family) with a name, depth, and an optional bag of _parts[]. Morphisms are parent→child arrows in the tree; the whole structure comes from parts-taxonomy.json compiled into window.TAXONOMY_DATA.
Selection playlist. An object is a finite set of taxonomy nodes (a playlist of branches). A morphism is include / remove under branch selection: right-click, Selection Mode taps, or the Select Entire Branch / Deselect Branch buttons in the info panel, which operate on entire subtrees.
Exports. An object is either (a) a catalog MPD (header box + 6-column grid of parts, taxonomy_catalog_*.mpd), or (b) a taxonomy-batch JSON manifest (nodes[] with parts[] carrying taxonomyPath). Morphisms are the export functions from a playlist of branches into these serialised worlds.
FUNCTORS
F — Branch selection → MPD catalog.
Domain: the Taxonomizer tree with user-marked selection on nodes.
Codomain: a single MPD file that lays out each unique part from the selected branches in a numbered catalog grid.
Action on objects: a set of branches ↦ an ordered list of distinct parts (deduped by path|filename).
Action on morphisms: adding/removing a branch in the playlist ↦ adding/removing the corresponding per-part blocks in the MPD. The COPY and DOWNLOAD buttons are two realizations of the same functor (clipboard vs. file).
G — Branch selection → JSON manifest.
Domain: same Taxonomizer + selection playlist.
Codomain: taxonomy-batch JSON with nodes[]; each node carries its path, depth, and enriched parts[] with taxonomyPath and any original fields (e.g. headRole, upperComplete).
Use: this is the bridge to Minifigurator and other -ators. A downstream script can treat it as a typed slice of the LDraw ontology and re-bucket parts into heads, torsos, hips, etc., mirroring minifig-library.json.
MINIFIG CHANNEL
H — Taxonomy slice → Minifig buckets.
H takes a taxonomy-batch JSON and constructs a local minifig library: a JSON with parts.heads, parts.torsos, parts.hips, parts.legs, and so on, using the same fields Minifigurator already understands (headRole, upperComplete, lowerComplete, includesArms, etc.).
Under H, a taxonomy branch that happens to be "MINIFIG HEADS" becomes a bucket of dial entries in Minifigurator, so the minifig family generator is grounded in the same ontology that Taxonomizer visualizes.
Playlist semantics.
Viewed together, Taxonomizer + exports + Minifigurator form a chain:
(taxonomy branches, inclusion) → (selection playlist) → (MPD catalog / JSON slice) → (minifig buckets / scenes).
This olog pins the meanings:
• A selection is a subfunctor picking regions of the world graph.
• An MPD catalog is a concrete slice of that graph, ready for GOLD/GRACE/WERE.
• A minifig family MPD is a higher-order scene built from those slices.

MENTO CAMERA OLOG — 702 / DESERT / 368
OVERVIEW
Aim. Port the robust MENTO camera pipeline from mento-glb-desert.html into the sleeker ai_studio_code-702 surface without losing 702's clarity.
Result. We reached feature parity on paper (MENTO shots, flips, bind-to-center, offsets, linear playback, capture), but the combined system became fragile and hard to reason about. This olog formally retires the 702 integration and designates mento-368.html as the new baseline.
MENTO-369: Scene presets + Grace lab.
mento-369.html mirrors 368's camera surface but boots straight into the GRACE sample GLB and exposes a SCENE PRESET switcher (GRACE / DESERT / BLANK). The CAMERA tab also has a LOAD GRACE SAMPLE button that drops the Searchers_Rider_Grounded_SpinFix.mpd manifest into the editor so shots + lights can be imported in one click.
DILEMMA
Too many coordinate authorities.
• GLB transform (scale / flip / zero-to-origin).
• Path anchor gizmo baked into keyframes.
• Slot-1 binding (pathGroup parented under the model).
• MENTO mapping (Flip X/Y/Z, Bind Ctr, SCL, shotOffset, TARE).
• OrbitControls target drift.

Each layer is reasonable alone, but stacked inside 702 they produced feedback loops: the spline “slipped”, doubled, or walked away as we rebuilt paths or re-bound to Slot 1. Control authority over the camera path was never single-sourced.
RESEARCH NOTES
What we successfully ported into 702:
• Structured !MENTO SHOT parsing → mentoShots model (label, POS, TGT, LENS).
• MENTO SHOTS list UI with click-to-jump POVs.
• Desert-style mapping: axis flips, mento-scale, bind-to-GLB-center, shotOffset, TARE-to-Slot-1.
• Keyframes built from transformed shots (pos/tgt/fov), not raw orbit snapshots.
• Linear keyframe playback (no Catmull for the actual camera), FOV + target interpolation, frustum helpers synced to the active segment.
• Recording pipeline using MediaRecorder with path-driven motion and separate REC length.
Where it still failed as a tool:
• Binding the path under Slot 1 while also re-centering to Slot-1 bounds caused subtle double transforms.
• Small UI changes (toggling Bind Ctr, rebinding path, TARE) could radically move the path in ways that were hard to predict from the surface.
• 702's compact chrome didn't have enough visual affordances (minimap, orbit HUD, preset snapshots) to make the composite state legible the way DESERT does.
• Fixes reduced specific bugs but increased conceptual load; the system felt like an experiment log, not a reliable instrument.
PIVOT TO 368
MENTO-368 as the new sensor surface.
Instead of forcing DESERT's full calibration stack into 702, we treat mento-368.html as a fresh control surface:
• Keeps the STUDIO palette (MODEL / PATH / REC colors) and panel layout.
• Reuses the best ideas from DESERT (structured shots, linear keyframe playback, frustums, capture) but re-designed for this UI from the start.
• Gives camera and path a single clear owner at any time, avoiding hidden double parenting and “slipping”.
This olog marks 702-as-lab-not-tool and 368 as the place to build forward.
368 MOBILE / ROTATION UX
From fussy gizmos to sculptural control.
• On mobile, mento-368.html and mento-369.html now stack viewport and panel with a fat, thumb-friendly splitter bar; you can drag it to let the panel temporarily cover most of the grid when you need to read or edit data.
• PATH editing separates selection, rotation, and POV: spline nodes and storyboard rows select a key; a dedicated POV button is the only way to jump the live camera into a shot.
• The rotation gizmo no longer hijacks the view. It purely sculpts each key's POS→TGT direction in space, while the big 16:9 timeline preview renders the key's frustum as ground truth.
• KEY DATA adds yaw / pitch dials and sliders per key, so camera aims can be tuned numerically or by thumb without fighting the 3D widget. Together these moves push 368 toward a calm, WYSIWYG camera instrument instead of a noisy 3D CAD rig.
368 CAPTURE / TIMING
Timing as an explicit tradeoff.
MENTO-368 treats camera motion as a virtual path and capture as a separate, heavier process.

• Preview uses real elapsed time: DURATION (S) in the CAMERA tab controls how long the camera takes to run from first to last key, driven by the app clock so scrubbing feels live.
• Capture uses deterministic stepping: when START CAPTURE runs with 2+ keys, the path is advanced in fixed 1/FPS steps for exactly SEC virtual seconds, so each key always lands at the same fraction of the move, even if the browser is slow.
• Real-world smoothness is bounded by device budget: each frame must render the GLB at the chosen resolution and be encoded at the selected Mbps; if that budget is exceeded, the browser may stutter even though the path math is clean.

Suggested presets.
• Desktop: 1080p, 24–30 fps, 5–8 Mbps, helpers hidden during capture; use 4K only on strong GPUs.
• Mobile / low power: 720p, 24 fps, 3–4 Mbps, one GLB loaded, FRUSTUMS + debug helpers off while recording.
Future work bundles these into explicit capture modes (SMOOTH / BALANCED / SHARP) so the tradeoffs are one click instead of a mental model.
